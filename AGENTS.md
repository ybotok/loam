# Working on loam itself

This file is for anyone — human or coding agent — changing the **source of loam**.

It is not the `AGENTS.md` loam writes. That one is generated by `src/core/agent.ts`, lands in a
*docs repo*, and describes how to use the tool. This one describes how to build it. If you are
editing `AGENTS_MD` in `src/core/agent.ts`, you are editing the other file's contents, not this
one.

## What loam is

A single-binary Node CLI that reads and writes a fleet's architecture and spec documents as plain
files. It has no server, no database, no network calls, and three runtime dependencies on purpose
(`commander`, `likec4`, `yaml`). Delete loam and the documents still make sense — that property is
the product, and it constrains every design choice below.

## The gate

Nothing is done until all of this is green:

```bash
npm run lint && npm run typecheck && npm test
```

Coverage thresholds are enforced separately and must also hold:

```bash
npm run test:coverage
```

`statements 91 · branches 82 · functions 95 · lines 93`. Do not lower a threshold to land a
change, and do not write a test purely to move a number. Report a red honestly; a truthful failure
is worth more than an engineered pass.

Run a single suite while iterating: `npx vitest run test/archive.test.ts`.
Run the CLI without building: `npm run dev -- status --json`.

## What is frozen

loam is published (`@ybotok/loam`, currently a `beta` prerelease). These are a contract, not
implementation details:

- **Command names and flags.** An agent somewhere has `loam validate --all` in a script.
- **Exit codes.** `0` success, `1` refusal or gating error.
- **The `--json` envelope.** `contractVersion`, `ok`, and `error.code` (`src/core/json.ts`).
  Adding a payload key is additive and allowed; changing or removing one is not.
- **Every stable code string** — the `ErrorCode` union in `src/core/json.ts` and the `IssueCode`
  family in `src/core/issue.ts`. Prose may be reworded freely. Codes may not.

Changing any of these means a CHANGELOG entry describing the change in the terms a user would
notice. Two tests exist to stop this drifting silently:

- `test/codes-drift.test.ts` — every stable code loam emits must appear in the agent-facing docs
  (`AGENTS_MD` and the slash-command bodies in `src/core/agent.ts`). A code that ships
  undocumented is a branch nobody was told about.
- `test/agent-commands-runnable.test.ts` — every `loam …` command loam *prints* is parsed against
  the real CLI. loam instructs agents; an instruction that does not parse is a defect.

## Layout and dependency direction

```
src/cli.ts        commander wiring; the only place that decides process exit
src/commands/     one module per CLI command — parse args, call core, print, set exit code
src/core/         everything else: a 7-level DAG with zero import cycles
```

- **`core/` must not print.** No `console.*`, no `process.exit`, no `process.argv`. A core module
  that prints cannot be reused by a second command or tested without capturing stdout. The one
  deliberate exception is `core/json.ts`, which *is* the output layer.
- **`core/` must never import from `commands/`.**
- **Keep the cycle count at zero.** It is currently zero and that is load-bearing: a cycle makes
  module-evaluation order decide behaviour. When a helper you need lives in a module far heavier
  than the helper, move the helper out rather than importing the weight — that is how
  `core/document-bytes.ts`, `core/records.ts` and `core/steps.ts` came to exist.

## Standards

- `docs/CODE-STYLE.md` — the conventions the compiler and linter cannot enforce, each with the
  defect it came from. Read it before a first change to `src/`.
- `docs/DESIGN.md` — module boundaries, what is an abstraction here and what is not, and which
  restructurings were considered and declined, with the reason.

## Comments

This codebase documents **why**, not what, in full sentences. The comments record the failure a
line prevents — that is why they are long, and why deleting one during a refactor loses
information the code cannot carry. A comment describing behaviour must be *corrected* when the
behaviour moves, never deleted. A false cross-reference is worse than no comment: it is how the
next reader stops looking.

## Tests

`test/helpers/harness.ts` is the fixture vocabulary — `makeProject`, `runLoam`, `coherentFixture`,
`treeHashes`, and the `LANDSCAPE` / `LIVING_SPEC` / `FEATURE_DELTA` constants. Use it; do not
invent a second harness.

Tests run in forked processes because commands resolve `loam.json` through `process.cwd()` and
each test `chdir`s. That is also why **module-level mutable state is a hazard** — a value cached at
import time leaks across tests and, in a long-running host, across invocations.

A behaviour change needs a test that fails before it and passes after. If you cannot convince
yourself of that, the test is not pinning what you think.

## Conventions

- Do not add a runtime dependency. It is a product decision, not a refactor.
- Do not commit `dist/`, `coverage/`, or a local `loam.json`.
- Never `git push --mirror` from this repository — the working tree may hold locally-excluded
  files that are deliberately not part of the public history.
- Releases are tag-driven and maintainer-only (`CONTRIBUTING.md`). Creating a tag or running
  `npm publish` is never part of an ordinary change.
