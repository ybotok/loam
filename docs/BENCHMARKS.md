# Benchmarks

Numbers behind performance claims in the CHANGELOG and ROADMAP. Every timing table here is produced
by `npm run bench:validate` (`scripts/bench-validate.ts`) against the built CLI, and is committed
together with the change it measures — a claim like "~Nx faster" divides one committed median by
another, never by a recollection. The last section is the other cost, the bytes an agent is handed;
its table is generated by `scripts/payload-sizes.ts`, and a test regenerates it on every run.

## The shape a fleet feels

The tables below are the method and the committed runs. This is what those numbers mean for somebody
operating a fleet — 2026-08, on a generated 120-service fleet with 400 and 800 op-linked landscape
edges and 10 active features (built CLI, 8-core laptop, idle, wall clock including Node startup — of
which ~0.16 s is Node itself): `loam list` **~0.45 s**, `loam validate --service <id>` — the command
each service repo's CI runs — **~0.6 s**, and `loam status` **~1.3 s** — it grades every active
feature's `delta.likec4`, so it costs about 0.11 s per feature *in flight* and is nearly flat in the
size of the fleet (the same 120 services with one active feature answer in ~0.34 s). The fleet gate
used to be the outlier: `loam validate --all` over 120 services took **~13–14 s** while it paid a
fresh LikeC4 workspace per service. Since the batched loader it parses the run's C4 documents in one
shared workspace and answers in **~0.7 s median** on the committed 120-service benchmark fixture —
the method, the machine and the committed runs are below (measured 2026-08-19). It is the docs
repo's own CI job and it is not on anybody's inner loop; on a machine whose cores are already busy,
expect meaningfully more.

**Re-measured 2026-10-28, and no longer true.** On a 12-thread Windows desktop, the same fixture's
`validate --all` takes **~18 s**, both at 0.2.0-alpha.16 and at the change that added this
paragraph (18.2 s and 18.3 s medians). The 0.7 s above describes the tree it was measured on, not
this one. The time has moved to the features. Every active feature's C4 merge is now previewed
(`delta.merge-refused`), and its post-merge project is staged so its `Covers:` lines resolve
against the map the merge would leave. On this fixture that is 20 staged projects (~13.5 s) and 80
parses of the map alone (~9.7 s), run concurrently: about 1 s of LikeC4 work per feature in flight.
The fixture had also stopped running at all once a missing `architecture/services.likec4` became
`subsystem.views-stale`, an error. The benchmark now runs `loam subsystem sync` before it times
anything. The other fleet shape, and what is left to win on both, is under "A fleet whose weight is
in the map". `test/scale.test.ts` gates a smaller fleet — 30 services, 10 features, 24
op-linked edges — under a 110 s wall-clock ceiling. That ceiling was calibrated against the
then-64-file parallel suite; the suite has grown since. It remains a blowup alarm for an
order-of-magnitude regression, not evidence that a two-fold slowdown is acceptable.

## Method

- **Fixture** — the synthetic fleet from `test/helpers/fleet-fixture.ts` at benchmark shape: **120
  services** (20 apiless / 40 documented / 40 sourced / 20 vouched) and **20 active features** — the
  scale suite's 5/10/10/5 + 10 shape with services ×4 and features ×2 (20/40/40/20 + 20). That is
  **141 `.likec4` documents** (1 landscape + 120 service models + 20 feature deltas) and **119
  op-linked edges** (the landscape's 99-call chain + 20 tagged feature edges). The fleet is clean:
  `validate --all` exits 0, so the runs measure grading, not error rendering.
- **Cold/warm policy** — one fresh `node dist/cli.js <args> --json` child process per run (real
  startup, no in-process warm LikeC4 state), sequential, on an otherwise idle machine; the OS page
  cache stays warm across runs.
- **Repetitions** — per command: 1 discarded warm-up, then 5 measured runs. Tables report the
  **median** of the five, with all five beside it.
- **Peak RSS** — sampled per run by polling `ps -o rss=` every 25ms; a run's peak is the largest
  sample, and the table reports the median of the five per-run peaks. Sampled, not exact
  (`/usr/bin/time -l|-v` would be exact but its flags and units differ across darwin/linux) — good
  to a few MB, which is enough for the hundreds-of-MB questions asked here.
- Every measured run is checked before its timing is kept: exit 0, parseable `--json`, `ok: true`,
  and `valid` not `false`. A failing run measures nothing.

## Baseline — one LikeC4 workspace per document (pre-batch)

Recorded before the `validate --all` batch loader landed, from the tree at the fixture-extraction
commit. This is the number the batch change's "≥2x" claim divides by.

Machine: darwin/arm64, 8× Apple M1, 8 GB RAM · node v24.13.1 · 2026-08-19

| command | median | runs (ms) | peak RSS (median of per-run peaks) |
|---|---|---|---|
| `loam validate --all --json` | 13748 ms | 13830, 13768, 13693, 13626, 13748 | 526 MB |
| `loam validate svc-21 --json` | 515 ms | 519, 510, 515, 513, 515 | 204 MB |
| `loam list --json` | 405 ms | 409, 403, 405, 403, 409 | 177 MB |

The 13.7s median reproduces the roadmap's 13–14s assessment: under `--all`, every service model,
feature delta and the landscape paid a fresh LikeC4/Langium workspace (~100ms each even warm), one
per document.

## After — one shared workspace for the whole `--all` run

Same machine, same fixture, same method, re-measured after `validate --all` started prefetching the
run's documents through `loadBatch` (`src/core/c4/workspace.ts`): one mkdtemp workspace, one
single-file project per document, one `LikeC4.fromWorkspace`. Single-service `validate` and `list`
keep their untouched per-path code, so their rows are the drift bound, not a claim.

Machine: darwin/arm64, 8× Apple M1, 8 GB RAM · node v24.13.1 · 2026-08-19

| command | median | runs (ms) | peak RSS (median of per-run peaks) |
|---|---|---|---|
| `loam validate --all --json` | 731 ms | 731, 727, 716, 731, 746 | 246 MB |
| `loam validate svc-21 --json` | 515 ms | 515, 513, 515, 513, 517 | 205 MB |
| `loam list --json` | 406 ms | 408, 408, 406, 404, 406 | 177 MB |

Exit-criteria arithmetic, against the baseline above:

- `validate --all`: 13748 ms → 731 ms = **18.8x faster** (criterion: ≥2x).
- `validate svc-21`: 515 ms → 515 ms = 0.0% drift (criterion: within 10%).
- `list`: 405 ms → 406 ms = +0.2% drift (criterion: within 10%).
- Peak RSS for `--all` **dropped** 526 MB → 246 MB: one workspace holding all 141 documents costs
  less than the serial loop's per-document workspaces, whose memory `dispose()` does not promptly
  return. The linear caveat stands: a fleet with far fatter documents scales this row linearly, and
  this table is the honest bound at the committed shape.

## A fleet whose weight is in the map

The fixture above stresses the number of documents: 120 small STANDALONE models around a
one-line-per-service map. A pilot fleet audited on 2026-10-28 had the opposite shape. It measured
`validate --all` at **56 s** and `validate --feature` at **27 s**: few, mostly empty, EXTENDING
models around a map of thousands of lines. An extending model is read inside a project of its own
(the whole `architecture/` project plus that one file), so the map is parsed once per service, and
the 120-service fixture could not see what that costs.

- **Fixture** — `npm run bench:validate -- --fixture map-heavy`, generated by
  `test/helpers/map-heavy-fixture.ts` with the pilot's counts and none of its names. It has 78
  services in 18 subsystems, 32 external systems, 40 stores, 86 groups, and 876 edges over 8
  relationship kinds and 50 tags. The landscape is 7,999 lines with 92 views, and a hand-written file
  of 78 more views sits beside it. All 78 models extend the map, and 60 of them are comment-only.
  `loam subsystem sync` writes the generated `subsystems.likec4` (18 views) and `services.likec4`
  (78 views) before anything is timed. There is one feature over 14 services with 125
  requirements. The fleet is clean (`likec4 validate` Valid over its 80 documents; loam exits 0),
  and `test/map-heavy-fleet.test.ts` keeps a scaled-down copy clean in the suite.
- **Method** — the built CLI, one fresh process per run, medians reported, as above, with one
  difference: the before/after table is interleaved (`--against <cli>`, below). The command is
  `npm run bench:validate -- --fixture map-heavy --cli <after> --against <before>`.

### Where the time went

A CPU profile of `validate --all` on this fixture (in-process, before the change, 55.5 s) put
**42.4 s in one call**: the prefetch's `loadProjectBatch`, which staged 78 per-service projects in
one LikeC4 workspace. That is 234 documents and 14 MB of source, because each project carries its
own copy of the ~180 KB `architecture/` project. Inside it:

- chevrotain parsing took ~11.5 s;
- Langium linking took ~11 s;
- LikeC4's `projectElements`/`isIncluded` took ~5.5 s. For every global-scope lookup it walks every
  document key in the workspace and checks project membership, so the cost grows with projects ×
  documents;
- garbage collection took ~5 s.

The rest of the run was the map project (~0.6 s) and the renderer-eye project (~1 s). The merge
preview parsed the map alone four times (~2.4 s). The other ~6 s was loam's own grading.

Sixty of those 78 projects were the map plus a comment-only file. That file declares nothing and
adds nothing to its project, so all such models now share **one** parse of the `architecture/`
documents, staged from the docs root as a per-service project is. Each model gets its own copy of
the answer, and `test/service-model-inert.test.ts` pins that copy deep-equal to the per-model load
it replaces, on a clean map and on a broken one. A file that only *looks* empty, such as one with an
unclosed block comment, keeps a project of its own. On the same fixture, the `--json` of
`validate --all`, `validate --feature`, `validate svc-3`, `validate svc-40`, `list` and `status` is
byte-identical before and after.

Machine: win32/x64, 12× AMD Ryzen 5 7600X, 32 GB RAM · node v24.13.0 · 2026-10-28. Built CLIs: 0.2.0-alpha.16
(`a94b3b7`, "before") and this change ("after"), run as
`npm run bench:validate -- --fixture map-heavy --against <before>`.

Other sessions' test suites shared the host while these ran, and a sequential run shows it: one
block of five before-runs of `validate --all` spread from 60 s to 123 s. So this comparison is
**interleaved**. Each command alternates the two CLIs: one warm-up each, then five rounds with the
order flipped every round. Load drift therefore lands on both sides alike, as the two columns' runs
below show by falling and rising together. Peak RSS is not reported, because the sampler shells out
to `ps` and this host has none.

| command | before (median) | after (median) | runs before (ms) | runs after (ms) |
|---|---|---|---|---|
| `loam validate --all --json` | 56528 ms | 20984 ms | 57364, 56671, 56528, 35864, 34885 | 21034, 20984, 21292, 14388, 14192 |
| `loam validate --feature FEAT-1 --json` | 20085 ms | 13741 ms | 12540, 12997, 21709, 20085, 20315 | 9081, 9511, 13764, 13741, 13763 |
| `loam validate svc-3 --json` | 3351 ms | 3299 ms | 3304, 3338, 3351, 3422, 3376 | 3273, 3299, 3292, 3301, 3328 |
| `loam validate svc-40 --json` | 3374 ms | 3279 ms | 3414, 3385, 3368, 3374, 3372 | 3279, 3232, 3312, 3167, 3337 |
| `loam list --json` | 2536 ms | 2377 ms | 2536, 2470, 2531, 2612, 2597 | 2338, 2352, 2439, 2567, 2377 |

- `validate --all`: 56.5 s → 21.0 s, **2.7x faster**. An earlier five-round interleaved run, at a
  quieter moment, measured 36.4 s → 14.0 s, the same 2.6x.
- `validate --feature`: 20.1 s → 13.7 s, **1.5x faster**. The feature touches fourteen services,
  ten of them placeholders, and those ten now cost one parse instead of ten. The rest is the
  per-feature merge preview below.
- `validate svc-3` (a drawn model), `validate svc-40` (a placeholder) and `list` are unchanged: a
  single service's project is one parse either way.

The pilot's own 56 s and 27 s come from a different machine and the fleet's real documents. That the
before column lands on 56 s here is a coincidence of this host's load. What this table supports is
the ratio.

What is left, measured after the change:

- The 18 models that draw an interior still parse the map once each: ~6.9 s for 19 projects
  in-process. Loading the drawn models together would be cheaper, but it would let one model's
  `extend` block resolve another model's references, which a per-service project must not do. So
  this has no fix as cheap and as exact as the placeholder case.
- Each active feature pays about 1 s of LikeC4 work: ~1.6 s here, ~18 s on the 120-service fixture
  with its 20 features. Two readers each compute the same merge preview: `delta.merge-refused` and
  the post-merge `Covers:` resolution. Each preview parses the living map alone and then the merged
  map, so the map is parsed four times per feature, and the living-map parse is the same text for
  every feature. **Recommendation:** memoise the preview per feature on the run's `FleetContext`,
  and hand `planLandscapeMerge` the prefetch's own parse of the living map instead of re-parsing
  it. That should cut the 80 parses on the 120-service fixture to about 21, with the findings
  unchanged by construction. It is not done here because it changes the merge-preview contract the
  archive also calls.

## What an agent is handed — payload sizes

Time is one cost; context is the other, and it is the one an evaluator can reproduce first. loam's
agent-facing surface is text: the docs repo's `AGENTS.md`, which a host may load into every turn;
the adopt brief; the version-matched workflow and reference pages `loam instructions` prints; and
the one-code answers `loam explain` gives. The table is each of them in bytes on stdout, and in
tokens at the rough bytes ÷ 4 rule — a real tokenizer differs, mostly with how much code and
punctuation a page holds.

- **Generated, not typed.** `npx tsx scripts/payload-sizes.ts --write` regenerates the block
  between the markers, and `--check` only compares. `test/docs-facts.test.ts` regenerates it on
  every run and fails when it differs from the committed block, so an edit to a protocol, a fix
  table or the brief that moves a number moves this table in the same commit.
- **The tree, not the machine.** Each command runs in process against `examples/docs`, through the
  same `buildProgram()` the binary runs, and the bytes are what a real process writes — checked
  against `node dist/cli.js … | wc -c` when the script was written. Two normalisations: the adopt
  brief and the context pack echo the docs repo's absolute path, which is counted as the 10-byte
  `/work/docs`; and the implementer briefs, which quote the fleet's files, read an LF copy of it,
  so a Windows checkout's CRLF does not move them. No clock, host or path enters the block; the
  date line above it is the last `--write`.
- **Each page as its slash command loads it**, placeholders filled with the example fleet's ids:
  `/loam-implement FEAT-101 payment-service` loads
  `loam instructions loam-implement FEAT-101 payment-service`.
- **`explain` is a distribution, not one number**: every code `loam explain --codes --json` lists,
  each looked up on its own with `loam explain <code> --json`.
- **A ceiling on the default forms.** The same test fails when any call in the form an agent makes
  it by default — no flag that narrows or widens it — prints 50,000 characters or more, the size
  past which Claude Code moves an MCP tool result into a file. Three calls are named exceptions with their reasons (the full adopt
  brief, `loam explain --codes` and the `loam-codes` page), and an exception that comes back under
  the line fails too, so the list only shrinks. That ceiling is why `loam-check` prints without its
  fix tables unless `--fix-tables` asks.

Reading it:

- **The orientation is the always-on cost, and its ceiling is a test.** `test/agents.test.ts`
  fails the build the day `AGENTS.md` crosses 12,000 bytes. Everything below it is fetched only
  when a task reaches it.
- **`loam-check`'s page is almost all per-code fix tables.** `--no-fix-tables` keeps the paragraph
  saying which scope graded them and drops the rows, and `loam explain <code> --json` answers the
  two or three rows a run actually reported. Loading the whole page to read one finding is the
  expensive way to ask.
- **The brief's fixed part is the same bytes for every service** — the code walk, the named checks
  and the statements of what nothing checks. A run over several services reads it once and asks
  `--targets` for the rest; the difference between the two brief rows is what that saves per
  service.
- **`loam explain --codes --json` is the whole vocabulary in one envelope**: a lookup table for
  tooling, not something to load into a session.
- **The briefs are called the way the `loam-implement` page calls them.** The example feature's
  `intent.md` is two kilobytes, so `--intent-ref` saves little here. Without the flag every brief
  carries the intent verbatim, and an intent grows with every decision and open question written
  into it: on a feature whose intent has reached two hundred kilobytes, the default leaf is that
  size whatever its unit. `test/intent-ref.test.ts` pins the ratio on a synthetic intent of that
  size, and the flag's CHANGELOG entry gives the bytes measured on a fleet shaped like the one that
  reported it. The page also passes `--outline` to `loam delta` and `loam context`, which no column
  here measures: the example's requirements are a few hundred bytes each, so an outline of them
  saves nothing worth a column, and the `--outline` CHANGELOG entry gives the bytes on a fleet whose
  largest service's requirements came to 334 KB.

What this table is not: a benefit. It prices what loam hands an agent and says nothing about what
that buys. No comparison of a session with loam against plan mode and an `AGENTS.md` alone has
been run or published yet, so none is claimed here.

## What the agent surface buys — behavioural evals

Payload sizes say what an agent is handed. They do not say whether it helps. The behavioural evals
measure that: the same request a person would type, run headless in a scratch copy of
`examples/docs`, once with the agent surface `loam init` lays down for Claude Code and once with
`AGENTS.md` alone. Each run is graded on its tool calls and the files it left, never on what it said.
The scenarios and their traps are in
[scripts/evals/README.md](https://github.com/ybotok/loam/blob/main/scripts/evals/README.md):
- adopt a service from its code without vouching;
- write open questions for a feature that contradicts a living rule;
- leave generated Gherkin alone;
- do not archive an unbuilt feature;
- find and fix a broken spine.

**No numbers are published yet.** A run costs money and is nondeterministic, so it runs at a
release (three runs per scenario and arm), and its table will appear here with the loam version,
the model and the date. Until then, the harness itself is tested (`test/evals.test.ts`), and
`npx tsx scripts/evals/run.ts --prepare-only` builds every workspace without calling a model.
